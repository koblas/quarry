## Traps
- S2d compares the until's LAST day with the default since; S3 compares the since's FIRST day with today; S2 compares since's first day with until's last day. Comparing raw parse results makes `--since 2024 --until 2024` an S2. (SCENARIO-13)
- `date_trunc('month', <DATE>)` is `TIMESTAMP` on DuckDB v1.5.5: cast to `DATE`. `s.id NOT IN (SELECT to_split_id ...)` with any NULL empties the view: use `NOT EXISTS`. `c.kind <> 'system'` drops uncategorized splits (NULL): use `IS DISTINCT FROM`. Category kind strings live only in `internal/importer`; duckstore uses SQL literals. `minimalRows`' transfers name `split-2`/`split-3`, not in `splits`. (SCENARIO-06)
- A column added mid-`CREATE TABLE` while the writer appends at the end silently writes values into the neighbouring column. (SCENARIO-01)
- A dev store synced before SCENARIO-06 lacks the 2b views, and a format-3 store built before `linked_tracking` (SCENARIO-27) lacks that column: `checkFormat` reads only `format_version`, so reads fail with a Catalog Error until `quarry sync` re-syncs; format 3 is unshipped so accepted, untested. (SCENARIO-01, 06, 27)
- Existing importer tests set only `PostedDate`; with entered NULL they still date by posted, so only exact-struct asserts on `Transactions` need a `PostedDate` bump. `store.Account`/`AccountBalance` test literals rely on `NotInReports` zero = in reports. (SCENARIO-01)
- Binding a local-zone `time.Time` to a DATE comparison: go-duckdb converts to UTC and can shift the day; bind civil days. The spec's sample spend table is illustrative: derive widths from the cells. The spend Long/Example text names `--by`/`--since`/`--account` before those flags exist; verbatim. (SCENARIO-09)
- Plan `-run` patterns are case-sensitive: importer tests are `Test_import_*`, cmd ones `Test_run_*`; use lowercase words. (SCENARIO-01)
- Importer dates are UTC calendar days but `current_date` is process-local: date-boundary tests belong at duckstore level with `store.Transaction.Date` at UTC midnight; cmd fixtures use dates a year ahead. (2a S04)
- Currency tie order: with only CAD/USD, DuckDB often returns tied rows sorted by chance, so a dropped `currency` ORDER BY term survives flakily. Pin each sort term with four currencies inserted USD, GBP, EUR, CAD and assert Rows and Totals (category, tag, month, cashflow tests do); check with `-count=20`. (REVIEW-01)
- `uncovered-diff.py` is blind to untracked files: `git add` first. Q-sentinels wrap `%w: %w`, so `errors.Unwrap` returns nil: use `errors.As`/`Is`. `v9fixture` writes `ZQUICKENID` raw: distinct non-zero per transfer leg. (Phase 1, 2a)
- `fakeReportStore.Query` ignores `maxRows`; a fixture writing at the store path must `CheckpointClose` before any read (DuckDB `InstanceCache`); a held reader shares the old inode. (2a S09, S02, REVIEW-01)

- `tags.name` is not unique and `split_tags` has no FK: tag SQL LEFT JOINs `tags` after `split_tags` and de-duplicates `(split_id, tag name)` before summing, or an untagged split and a dangling link look the same and two same-named tags double-count. (SCENARIO-11)
- A `strftime(...)` expression passed as `spendingQuery`'s key lands inside `GROUPING()`/`GROUPING SETS`/`ORDER BY`: month uses a dedicated query exposing a key column. The `YYYY-MM` label must come from SQL (a DATE scanned into `sql.NullString` is RFC3339 text) and match Go's `monthLabelLayout` byte for byte, or every month prints `0.00` beside lost real rows; only the DuckDB-backed acceptance test sees that. (SCENARIO-12)

- An empty `AccountIDs` means every account: filtering excluded accounts out in `report` turns "all named excluded" into "count everything". `spendingQueryFrom` binds positional `?`, tag queries `$1/$2`: a filter placed in the FROM subselect binds out of order; empty list must never render `IN ()`. `IN (...)` hides duplicate ids, so dedupe is provable only on `Spending.Accounts` length/order. `report` fakes share one `err` across Accounts and Spending. (SCENARIO-14)

- Savings-rate SQL guards with `CASE WHEN income > 0`; the integer `//` divides by `2 * income`, and DuckDB yields NULL (not an error) on division by zero, so the zero-income NULL does not depend on evaluation order. Do not swap to `/` or `ROUND` (float, negative zero, ties). Mutation: flipping the guard to `< 0` is caught by `Test_cash_flow_has_no_savings_rate_when_income_is_zero_or_less`. (SCENARIO-20)
- `SUM(...)` over a `CASE` with no matching row is NULL, not 0: COALESCE before the cents cast. Year/month label text must equal Go's `2006`/`2006-01` byte for byte or every period prints `0.00` beside lost rows. (SCENARIO-20)
