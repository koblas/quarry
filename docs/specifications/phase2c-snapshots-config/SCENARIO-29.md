Contract (`quarry sync`, `quarry sync --from <id|path>`; copy verbatim from spec `### Sync auto-prune`):
- Store built: exit 0; stdout gains `Pruned    …` after the Transfers block iff >= 1 snapshot was deleted; `--json` `pruned` = `{keep, deleted[], failed[]}` after `store`.
- A delete failure or an unlistable folder: one `quarry: warning: …; run quarry snapshots prune to try again` per fault on stderr (also in `warnings[]`, no prefix, after CF2), exit 0.
- Interrupted with snapshots still to delete: stderr `quarry: sync interrupted while deleting old snapshots; the store was rebuilt; run quarry snapshots prune to finish`, exit 1.
- Schema mismatch, validation failure, any refusal: nothing deleted (orphans included), no Pruned line, `pruned: null`, exit as today.

No new port or adapter: deletes stay on `WithRemove` (`snapshot.go:96`), the listing on `listFolder`; step-5 survey not applicable.

## Handoff

**Binding decisions** — a later scenario must not contradict these without saying so:
- The prune hangs off `importVerified`'s success tail and nowhere else — `Sync` failure (`import.go:94-96`), `--from` mismatch (`from.go:68-70`), validation and store refusals (`import.go:113-120`) all return before it, so "a failed sync deletes nothing" is structural
- Auto-prune never calls `planPrune`, `markStore` or `BuiltFrom`: the built snapshot is `manifest.Snapshot.Path` fed to `markStoreSnapshot` (U6 path then ID, U6b nothing) — a store read could turn a finished sync into the cannot-tell refusal
- Keep is the Server option `WithAutoPrune(keep)`; unset = no auto-prune — `snapshot` may not import `config`, and the 51 existing `SyncAndImport`/`ImportFrom` test calls stay behaviour-identical. `cli.ServerFactory` takes `opts ...snapshot.Option`
- Under `WithAutoPrune` (sync always sets it) `Outcome.Pruned` is nil iff no store was built (`pruned: null`), non-nil with empty lists for nothing-to-delete and cannot-list; without the option it stays nil
- Orphan sweep runs in auto-prune on uninterrupted runs only — P2c-7 is one rule, prune's Long says "as sync does", and it clears U1 leftovers; never after a failed sync
- ctx is checked before every pair, the first included; an ended ctx with nothing beyond the cap stays a plain success (`sync_and_import_test.go:280` pins it)

**Needs ruling before run B2** (plan assumes the prune precedent, U4 / SCENARIO-28):
- R1: mid-prune interrupt — stdout prints the result blocks and a Pruned line for what was deleted; `--json` prints the document with `pruned` as it stands; stderr: warnings, then the interrupt line; exit 1. Same line when the ctx ended before the first delete
- Derived by composition, not escalated: partial failure prints the line for the successes only; `beyond the newest one and the store's own`; cannot-list under `--json` is `{"keep":N,"deleted":[],"failed":[]}`

**Left unbuilt** — named so nobody assumes it exists:
- A lock between a sync's auto-prune and a concurrent `snapshots prune` or sync — STATE open debt, unowned
- A `--keep` flag on `sync` — not in the spec

**Traps** — things that look right and are not:
- Fixture IDs must sort older than the ID sync mints from `time.Now()`: `fiveSnapshots()` reaches ID `20260930T141502Z_2` and `list_test.go`'s `idNewest` is `20260930T141502Z`; a fixture newer than the real snapshot puts the built one beyond the cap (`and the store's own`). Use year-2000 IDs wherever a test takes a real snapshot; `ImportFrom` tests mint no ID and may reuse the constants
- `onlyFileWithSuffix` fails once fixtures share the folder; find the real snapshot as `manifestOtherThan` does (`run_import_runs_test.go:125`). `syncBundle` now prunes at 12
- `Prune`'s loop (`prune.go:124-130`) always attempts the first snapshot because the store read checked ctx; reused as is, a Ctrl-C during the build still deletes one file
- `osreason.Reason` on `listFolder`'s refusal gives the refusal's own text when the cause is not a `*fs.PathError`: take the reason from the cause
- A fake Importer writes no store: only `countingProbe` can see a store read; a real-store test passes either way
- `writeStatusFixtureBundle` leaves a transfer warning on stderr; SCENARIO-33 asserts stderr whole, so use `v9fixture.OpenBundle`
- The cannot-list folder is 0300, not 0100: snapshots open `mode=ro` without `immutable`, and SQLite may need to create a sidecar file beside a WAL-mode snapshot
